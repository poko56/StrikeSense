# StrikeSense — สรุปเชิงเทคนิคเฉพาะส่วน AI (สำหรับนำเสนอ)

เอกสารนี้สรุปเฉพาะฟังก์ชัน AI ของ StrikeSense: ทำอะไร ทำงานอย่างไร ใช้งานอย่างไร
และมีข้อจำกัดตรงไหน ตัวเลขทุกตัวในเอกสารนี้อ้างอิงจากโค้ดและ pipeline จริงในโปรเจกต์
ไม่ใช่ค่าประมาณ

---

## 1. ภาพรวม: AI ทำอะไรให้

ระบบมีเซ็นเซอร์ IMU 4 ตัว (มือซ้าย/ขวา แข้งซ้าย/ขวา) ส่งข้อมูล 400 Hz เข้ามาที่ Main Node
สิ่งที่ AI เพิ่มเข้ามาคือ **การบอกว่าอาวุธที่เพิ่งออกไปนั้นคือท่าอะไร** พร้อมระดับความมั่นใจ

แยกให้ชัดว่าอะไรคือ AI อะไรไม่ใช่:

| ส่วน | เป็น AI ไหม | ทำอะไร |
|------|-------------|--------|
| วัดแรง (g) และความเร็วเชิงมุม (°/s) | ไม่ใช่ | อ่านตรงจาก IMU |
| ตรวจจับว่า "มีการออกอาวุธ" | ไม่ใช่ | detector เชิงกฎ (rule-based) |
| บอกว่าเป็นท่าอะไร | **ใช่** | 1D-CNN ทำนายจากรูปคลื่นการเคลื่อนไหว |
| คะแนนต่อหมัด 0–100 | ไม่ใช่ | สถิติเทียบกับท่าเดียวกัน (ใช้ผลจาก AI มาเลือกกลุ่มเปรียบเทียบ) |

จุดขายทางเทคนิคที่ควรพูด:

- **โมเดลรันในเบราว์เซอร์ทั้งหมด** ไม่ต้องต่อเน็ต ไม่ส่งข้อมูลออกนอกเครื่อง
- **ไม่ใช้ TensorFlow.js** — เขียน inference engine เอง (`dashboard/src/ainet.js`)
  ขนาดเล็ก ทำงาน offline ตรวจสอบแล้วว่าผลตรงกับ Keras ที่ระดับความคลาดเคลื่อน 1e-6
  (`ml_pipeline/verify_web_model.py`)
- **เปลี่ยนโมเดลได้โดยไม่ต้อง flash เฟิร์มแวร์** โมเดลเก็บเป็นไฟล์ JSON บน SD card
  ของ Main Node และอัปโหลดผ่านหน้าเว็บ

## 2. เส้นทางข้อมูลตั้งแต่ต้นจนจบ

```
IMU 4 ตัว @400 Hz
   │  ESP-NOW
   ▼
Main Node (ESP32-S3)
   │  WebSocket (binary frames)
   ▼
เบราว์เซอร์
   ├─ Detector v2  ── ตัดสินว่า "ออกอาวุธแล้ว" + ตัดหน้าต่างเวลา
   ├─ Normalise    ── ใช้ mean/std ชุดเดียวกับตอนเทรน
   ├─ 1D-CNN       ── ทำนายความน่าจะเป็นของแต่ละท่า
   ├─ Physics prior── ถ่วงน้ำหนักด้วยแรง/ความเร็วจริง
   ├─ Limb mask    ── ตัดท่าที่แขนขาข้างนั้นทำไม่ได้
   └─ Naming policy── ตัดสินว่าจะตั้งชื่อท่าหรือบอกว่า "ไม่ระบุ"
```

ฝั่งเทรน:

```
Data Logger (หน้าเว็บ) → strike_*.csv (IMU ดิบ 400 Hz + ป้ายท่า + slot)
   → ml_pipeline/train_model.py
   → strike_web_model.json  (อัปโหลดเข้าแดชบอร์ด)
   → confusion_matrix.png   (ดูว่าโมเดลสับสนท่าไหน)
```

## 3. สเปกโมเดล

| หัวข้อ | ค่า |
|--------|-----|
| สถาปัตยกรรม | 1D-CNN (Conv1D → BatchNorm → MaxPool → GlobalAvgPool → Dense) |
| Input | 160 × 6 = หน้าต่าง 160 ตัวอย่าง @400 Hz คือ **400 มิลลิวินาที** |
| Features | `ax, ay, az, gx, gy, gz` เท่านั้น |
| Normalisation | per-axis standardisation ด้วย mean/std จากชุดเทรน (ฝังในไฟล์โมเดล) |
| รูปแบบไฟล์ | JSON `format: "strikesense-web/1"` |
| เทรน | 120 epochs (early stopping), batch 32, class weights แก้ข้อมูลไม่สมดุล |
| Augmentation | สุ่มคูณ gain 0.85–1.15 ต่อหน้าต่าง |

**หมายเหตุสำคัญ: `slot` ไม่ใช่ feature** — โมเดลไม่รู้ว่าข้อมูลมาจากมือหรือแข้ง
เจตนาให้เป็นแบบนั้น เพราะจะได้เรียนรู้ "รูปร่างการเคลื่อนไหว" ไม่ใช่จำว่าเซ็นเซอร์ตัวไหน
ส่วนการกันคำตอบผิดข้ามแขนขาไปจัดการที่ layer ถัดไป (ข้อ 6)

### โหมดความละเอียดของคลาส

| โหมด | จำนวนคลาส | รายละเอียด |
|------|-----------|------------|
| `coarse` (ค่าเริ่มต้น) | 5 | Punch · Elbow · Knee · Kick · Teep |
| `coarse_lr` | 10 | 5 อาวุธ × ซ้าย-ขวา |
| `fine` | ~21 | Jab, Cross, Hook, Uppercut, Elbow-Chop/Slash/Up/Thrust/Spear/Spin, Knee-Straight/Diagonal/Curve/Fly, Kick-Straight, Roundhouse, Kick-Low, Kick-Spin, Kick-Heel, Teep, Teep-Side, Teep-Back |

ทุกโหมดมีคลาสพิเศษเพิ่มอีก 2 ตัวเสมอ:

- **Idle** — ยืนนิ่ง ไม่ได้ออกอาวุธ
- **Move** — ขยับแต่ไม่ใช่การออกอาวุธ (ก้าวเท้า เปลี่ยนสแตนซ์ ตั้งการ์ดใหม่)

สองคลาสนี้คือกลไกกันการตั้งชื่อมั่ว ถ้าไม่มี `Move` โมเดลจะไม่มีคำตอบที่ถูกต้องให้เลือก
สำหรับขาที่ขยับโดยไม่ได้เตะ แล้วจะไปตอบเป็นท่าเตะที่ใกล้เคียงที่สุดแทน

## 4. Detector v2 — จุดที่กำหนดคุณภาพทั้งระบบ

โมเดลจะดีแค่ไหนขึ้นกับว่า "ตัดหน้าต่างเวลาตรงไหน" ถ้าตัดผิดจุด โมเดลจะเห็นคนละช่วง
กับที่เคยเทรนมา เรื่องนี้จึงถูกทำเป็นโมดูลแยก และ**บังคับให้ฝั่ง JavaScript กับฝั่ง Python
ใช้กฎเดียวกันเป๊ะ** มีเทสต์ตรวจความตรงกันที่ `ml_pipeline/test_detector_parity.py`

พารามิเตอร์ (ตรงกันทั้งสองฝั่ง):

| ค่า | ความหมาย |
|-----|----------|
| `armG = 5.0` | dynamic g (หักแรงโน้มถ่วงออกแล้ว) ที่ทำให้เริ่มค้นหายอด |
| `searchMs = 80` | ถ้าไม่เจอยอดใหม่ภายใน 80 ms ให้สรุปว่ายอดนั้นคือจุดกระทบ |
| `releaseG = 2.0` | ต้องตกกลับต่ำกว่านี้ก่อน ถึงจะนับครั้งถัดไปได้ |
| `refractoryMs = 400` | ระยะห่างขั้นต่ำระหว่างสองครั้งของแขนขาเดียวกัน |

### ทำไมเวอร์ชันแรกถึงใช้ไม่ได้ (เนื้อหานี้เล่าได้ดีในการนำเสนอ)

v1 ใช้กฎง่ายๆ คือ "เกิน 3.0 g เมื่อไหร่ = ออกอาวุธ" มีปัญหาสองข้อ:

1. **`|accel|` รวมแรงโน้มถ่วงอยู่แล้ว** แขนขาที่อยู่นิ่งอ่านได้ 1.0 g อยู่แล้ว
   เกณฑ์ 3.0 g จึงเท่ากับ 2.0 g จริง ซึ่ง IMU ที่แข้งทะลุค่านี้ได้จากแค่การเดิน
2. **จับที่จุดตัดครั้งแรก ไม่ใช่จุดสูงสุด** วัดจากข้อมูลจริง: เฟรมแรกของท่าเตะตัดที่ ~5 g / 260 dps
   แต่จุดกระทบจริงมาถึงอีก ~250 ms ให้หลังที่ ~12 g / 630 dps
   v1 จึงประทับเวลาไว้ที่ "ช่วงเก็บขา" แล้วส่งช่วงนั้นให้โมเดลดู — **โมเดลไม่เคยเห็นจุดกระทบเลย**

ผลคือ 81–92% ของจุดที่ v1 ตรวจจับได้ในไฟล์บันทึกท่าเตะ อยู่ติดเพดาน refractory พอดี
แปลว่าเตะหนึ่งครั้งถูกตัดเป็น 3–4 หน้าต่าง ส่วนใหญ่เป็นการเคลื่อนเท้า
โมเดลจึงเรียนรู้ว่า "แข้งขยับ = เตะ" ซึ่งเป็นเหตุผลว่าทำไมการเดินถึงถูกนับเป็นท่า

v2 แก้ด้วยการหักแรงโน้มถ่วงออก ใช้ hysteresis และ **ตามหายอดจริง**
(เจอยอดใหม่เมื่อไหร่ให้รีสตาร์ตตัวจับเวลา) จึงตามการเคลื่อนไหวไปจนถึงจุดสูงสุดได้

## 5. Physics prior — คืนข้อมูลที่ตั้งใจให้โมเดลลืม

ตอนเทรนมีการสุ่ม gain 0.85–1.15 เพื่อให้ Hook อ่านว่าเป็น Hook ทั้งที่ 6 g และ 11 g
ซึ่งถูกต้องสำหรับ "รูปร่างท่า" แต่ผิดสำหรับท่าที่ต่างกันที่ **ขนาดแรง** เป็นหลัก

วัดจากข้อมูลจริงที่จุดกระทบ:

| คู่ที่โมเดลสับสน | ค่าที่วัดได้ | Cohen's d |
|------------------|--------------|-----------|
| Elbow-Up vs Kick-Low | 7 g / 604 dps vs 18 g / 843 dps | 2.28 |
| Uppercut vs Hook | 8 g / 628 dps vs 16 g / 954 dps | 1.13 |

ทั้งสองคู่แยกกันได้ชัดด้วยขนาดแรงล้วนๆ จึงมีการ fit **Gaussian หนึ่งตัวต่อคลาส**
บน log ของ (peak |accel|, peak |gyro|) แล้วนำมารวมกับผลของ CNN **ใน log space**
โดยน้ำหนักถูกเลือกจากการวัดความแม่นบนชุด validation — ถ้าไม่ช่วย น้ำหนักจะถูกปรับเป็น 0
และโมเดลตอบเองล้วน

ต่างจากวิธีเดิมตรงไหน: ของเดิมเป็นบันไดเงื่อนไขเขียนมือ (`peakG > 9 → ศอก`)
ไม่มีการวัดรองรับ และตอบด้วยความมั่นใจเท่ากันทุกกรณี

**สิ่งที่วิธีนี้แก้ไม่ได้ และไม่ได้อ้างว่าแก้** — คู่ที่ต่างกันที่รูปร่าง ไม่ใช่แรง:
Elbow-Chop vs Elbow-Slash (d 0.53), Jab vs Cross (d 0.53), Roundhouse vs Kick-Low (d 0.46)
ไม่มีเกณฑ์แรงใดแยกคู่พวกนี้ได้

## 6. Limb mask — ตัดคำตอบที่เป็นไปไม่ได้

เพราะ `slot` ไม่ใช่ feature โมเดลจึงตอบ "Jab" ให้หน้าต่างที่มาจากแข้งได้
มวยไทยตัดสินเรื่องนี้ได้โดยไม่ต้องใช้โมเดล: มือออกหมัดกับศอก ขาออกเข่า เตะ ถีบ

ระบบจึง mask คลาสที่แขนขานั้นทำไม่ได้ออกก่อนทำ argmax ไม่มีต้นทุนเพิ่ม
แต่ตัดคำตอบผิดออกไปทั้งหมวด ข้อมูล `limbs` เดินทางมากับไฟล์โมเดล
ส่วนไฟล์รุ่นเก่าที่ยังไม่มีข้อมูลนี้จะ fallback ไปใช้การจับคู่จากชื่อคลาส

Slot ตายตัว: `1 = มือซ้าย · 2 = มือขวา · 3 = แข้งซ้าย · 4 = แข้งขวา`

## 7. นโยบายการตั้งชื่อ / การขอไม่ตอบ

มีสองสาเหตุที่ระบบจะขึ้นว่า "ไม่ระบุ" และสองอันนี้ไม่เหมือนกัน:

1. **Idle / Move** — โมเดลบอกว่าหน้าต่างนี้ไม่ใช่ท่าเลย
   ตัวนี้กันการบันทึกถุงมือที่ตกพื้น การจับเซ็นเซอร์ปรับตำแหน่ง หรือการลงเท้าแรงๆ
   ว่าเป็นหมัด — **บังคับใช้เสมอ ปิดไม่ได้**
2. **ความมั่นใจต่ำกว่าเกณฑ์** (`MIN_CONF = 0.35`) — เป็นการออกอาวุธจริง
   แต่โมเดลบอกไม่ได้ว่าท่าไหน ตัวนี้ผู้ใช้ปิดได้ด้วยสวิตช์ "ตั้งชื่อทุกครั้ง"

วัดบนชุด held-out ด้วยโมเดลที่ใช้งานจริง (675 การออกอาวุธจริง, 1422 หน้าต่างนิ่ง):

| การตั้งค่า | ตั้งชื่อ | ถูกต้อง | ได้ชื่อที่ถูกจริง |
|-----------|---------|---------|------------------|
| เปิดเกณฑ์ความมั่นใจ | 545/675 | 87.3% | 476 ครั้ง |
| ปิดเกณฑ์ | 668/675 | 80.4% | **537 ครั้ง** |
| ปิดเกณฑ์ + ปิด Idle ด้วย | 675/675 | 80.1% | 541 ครั้ง — แต่หน้าต่างนิ่งทั้ง 1422 อันก็ได้ชื่อท่าไปด้วย |

ประเด็นที่น่าพูด: **การปิดเกณฑ์ทำให้ได้ชื่อที่ถูกต้องมากขึ้น ไม่ใช่น้อยลง**
ความแม่นต่อชื่อลดลงก็จริง แต่ครอบคลุมมากขึ้นจนคุ้ม ส่วนการปิด Idle ด้วยนั้น
ได้เพิ่มอีกแค่ 4 ครั้ง แลกกับการเสีย safety net ทั้งหมด จึงไม่เปิดให้เลือก

นอกจากนี้ หน้าเว็บยังบอกตรงๆ ว่า **โมเดลตัวที่โหลดอยู่แยกได้กี่ท่าและท่าอะไรบ้าง**
เพื่อไม่ให้เข้าใจผิดว่าคำตอบที่ได้คือการวัด ทั้งที่จริงเป็นการเทียบเคียงกับท่าที่ใกล้ที่สุด
ที่มีในโมเดล (เช่น ยิงเข่าใส่โมเดลที่เทรนมาแต่ท่าเตะ)

## 8. คะแนนต่อหมัด 0–100

ไม่ใช่ AI แต่ใช้ผลจาก AI มาเลือกกลุ่มเปรียบเทียบ จึงควรเล่าคู่กัน

คะแนนบอกว่า **หมัดนี้เทียบกับหมัดท่าเดียวกันในข้อมูลที่บันทึกไว้เป็นอย่างไร** โดย 50 คือค่ากลาง
เหตุผลที่ต้องเทียบเป็นรายท่า: uppercut ลงประมาณ 9.5 g ส่วน cross ประมาณ 14.2 g
ถ้าใช้กฎเดียว "แรง = คะแนนสูง" uppercut จะถูกตีว่าอ่อนทุกครั้ง และ cross จะได้คะแนนเกินจริงทุกครั้ง

- ใช้ z-score บน log ของสองปริมาณ: **power** (peak |accel|) และ **speed** (peak |gyro|)
- `score = 50 + 22 × mean(z_power, z_speed)` ตัดที่ 1–100
- 1 SD เหนือค่าเฉลี่ยของท่านั้น ≈ 72 คะแนน · 2 SD ≈ 94 คะแนน
- ค่าอ้างอิงรายท่ามาจาก block `physics` ที่ pipeline fit ไว้และฝังมากับไฟล์โมเดล
  ไม่ใช่เกณฑ์ที่เดาเอา
- ถ้ายังไม่ได้โหลดโมเดล หรือหมัดนั้นไม่มีชื่อท่า จะเทียบกับค่ารวมทุกท่าแทน
  (11.6 g และ 846 °/s) ซึ่งอ่อนกว่าแต่ยังตรงไปตรงมา

## 9. วิธีใช้งานจริง (ลำดับสาธิต)

### 9.1 เก็บข้อมูลเทรน

1. เปิด Developer mode (แท็บ **ระบบ** หรือกดปุ่ม `d`)
2. การ์ด **AI TRAINING · DATA LOGGER** → เลือกท่าที่จะบันทึก → **เริ่มบันทึก** → ออกอาวุธ → **หยุด**

4. ทำให้ครบทุกท่า ทั้งซ้ายและขวา

Logger จะเขียนแถวของแขนขาที่ **ไม่ได้** ออกอาวุธเป็นคลาส `Move` ให้เองด้วย

### 9.2 เทรน

```bash
cd ml_pipeline
pip install -r requirements.txt
python train_model.py --data "./data/*.csv"
```

ได้ผลลัพธ์:

- `strike_web_model.json` — ไฟล์ที่อัปโหลดเข้าแดชบอร์ด
- `strike_model.h` — ทางเลือกสำหรับฝังบน ESP32 (TFLite Micro, int8)
- `confusion_matrix.png` — ดูว่าสับสนท่าไหน

ถ้าแก้ขนาดหน้าต่างหรือโครงโมเดล ให้รัน `python verify_web_model.py`
เพื่อยืนยันว่า inference ฝั่งเบราว์เซอร์ยังตรงกับ Keras

### 9.3 ติดตั้งโมเดลและใช้งาน

1. เปิดแดชบอร์ด → การ์ด **AI MODEL · ตรวจจับท่า**
2. **⬆ เลือกไฟล์โมเดล** → เลือกไฟล์ `.json`
3. สถานะขึ้น `พร้อม · N ท่า · หน้าต่าง 160×6` และเปิดสวิตช์ตรวจจับให้อัตโนมัติ
4. ออกอาวุธ — ระบบแสดงชื่อท่า + % ความมั่นใจ + แถบความน่าจะเป็นของทุกคลาส

### 9.4 คลังโมเดลบน SD card

โมเดลถูกเก็บไว้บน SD ของ Main Node ทำให้:

- เก็บได้หลายโมเดล เลือก active ทีละตัว
- **สลับโมเดลได้จากหน้าเว็บ ไม่ต้อง flash เฟิร์มแวร์ใหม่**
- ทุกเครื่องที่เชื่อมต่อได้โมเดลเดียวกันอัตโนมัติ
- ลบโมเดลที่ไม่ใช้ได้จากหน้าเว็บ

เบราว์เซอร์ยัง cache โมเดลไว้ใน localStorage ด้วย ถ้าดึงจากเครื่องไม่ได้ก็ยังใช้ตัวที่เคยโหลดไว้ได้

## 10. ข้อจำกัดที่ควรพูดเอง ก่อนโดนถาม

- **โมเดลตอบได้เฉพาะท่าที่เคยเห็น** ท่าที่ยังไม่ได้เก็บข้อมูลจะถูกตอบเป็นท่าที่ใกล้เคียงที่สุด
  นี่คือการเทียบเคียง ไม่ใช่การวัด หน้าเว็บเขียนกำกับเรื่องนี้ไว้ชัดเจน
- **คู่ท่าที่ต่างกันที่รูปร่างล้วนๆ ยังแยกยาก** — Jab vs Cross, Elbow-Chop vs Elbow-Slash,
  Roundhouse vs Kick-Low ต้องเก็บข้อมูลเพิ่มและเทรนใหม่ ไม่ใช่ปรับเกณฑ์
- **แรงคือค่าที่วัดจริงจาก IMU เสมอ** ไม่ใช่ค่าที่ AI ทำนาย ส่วนนี้ไม่มีการเดา
- **ความแม่นขึ้นกับข้อมูลเทรน** ตัวเลข 80–87% ข้างต้นมาจาก dataset ชุดปัจจุบัน
  ผู้ใช้คนอื่น สรีระอื่น หรือการรัดเซ็นเซอร์ต่างออกไป ควรเก็บข้อมูลของตัวเองเพิ่ม
- **หน้าต่าง 400 ms ตายตัว** ท่าที่ยาวกว่านั้นจะถูกตัดที่จุดกระทบ ซึ่งเป็นการออกแบบ
  ไม่ใช่ข้อบกพร่อง แต่ควรรู้ไว้

## 11. คำถามที่มักโดนถาม

**ถาม: ใช้ TensorFlow.js หรือเปล่า**
ไม่ใช้ เขียน forward pass เอง รองรับ conv1d, batch_normalization, max_pooling1d,
global_average_pooling1d, flatten, dense, dropout, activation
ตรวจสอบแล้วว่าผลตรงกับ Keras ที่ระดับ 1e-6

**ถาม: ข้อมูลถูกส่งขึ้น cloud ไหม**
ไม่ ทั้งการ inference และการเก็บข้อมูลอยู่ในเครื่องทั้งหมด ระบบทำงานได้โดยไม่ต้องมีอินเทอร์เน็ต

**ถาม: ทำไมไม่รันโมเดลบน ESP32 ไปเลย**
ทำได้ (pipeline ปล่อย `strike_model.h` แบบ int8 ให้ด้วย) แต่การรันในเบราว์เซอร์
ทำให้เปลี่ยนโมเดลได้โดยไม่ต้อง flash และมีแรงประมวลผลเหลือเฟือกว่า
ส่วน ESP32 เอาไว้ทำงานที่มันถนัดคือรับวิทยุและเขียน SD

**ถาม: ทำไมต้องมีคลาส Idle กับ Move**
เพราะถ้าไม่มี โมเดลไม่มีคำตอบที่ถูกต้องให้เลือกสำหรับการเคลื่อนไหวที่ไม่ใช่การออกอาวุธ
มันจะไปตอบเป็นท่าที่ใกล้ที่สุดแทน ซึ่งคือสาเหตุที่การเดินเคยถูกนับเป็นเตะ

**ถาม: เพิ่มท่าใหม่ต้องทำอะไร**
เก็บข้อมูลท่านั้นด้วย Data Logger → เทรนใหม่ → อัปโหลดไฟล์ใหม่ ไม่ต้องแตะเฟิร์มแวร์
